# 自动化临床文书：工作流自动化原型

> 一个由临床场景问题出发、采用 AI-assisted coding 完成的个人技术验证项目。探索如何将临床文书中的重复操作拆解为可复用的任务，并通过 OCR、文本处理与工作流编排辅助执行。

**项目状态：原型验证阶段（Prototype）**  
**项目周期：2026 年 7 月—9 月的集中开发与测试**  
**主要方向：临床工作流分析、OCR/信息提取、文本结构化、桌面自动化、Workflow 编排**

> 免责声明：本项目不是医疗软件或临床决策支持系统，未部署至生产环境。它不自动作出诊断或生成关键临床事实，生成或整理的文书内容必须由医务人员核对确认。本项目不应用于真实患者数据处理或实际临床决策。

---

## 1. 项目缘起：一个医生，多个系统，以及反复搬运的信息

想象一个普通的临床工作日：医生准备完成入院记录、病程记录、出院记录或病案首页填写。完成一份文书前，可能需要查看既往病历、了解病情变化、查询检验和检查结果、核对医嘱状态，再将信息整理后填写到目标文书中。

这些信息并不总在同一处：有些在 HIS 或 CIS 等系统内，有些来自既往电子病历，有些来自院外文书、纸质报告或手机拍摄的图片。医生需要不断切换页面、定位字段、复制内容、整理格式和核对状态。除了诊疗判断，医生也容易变成反复在不同窗口之间“搬运信息的人”。

在我接触的临床工作流中，文书与系统操作可能占据相当多的工作时间；这一判断是项目的实际场景观察，并非对所有医院或医生的统计结论。

**项目的出发点不是让机器代替医生，而是让机器尽可能承担重复、明确、可验证的操作，把专业判断和最终确认留给医生。**

## 2. 项目目标：把复杂任务拆成可复用的原子步骤

不同文书的目的不同，所需信息和填写顺序也不同。因此，本项目没有把所有操作写成一条不可拆分的长脚本，而是尝试按照文书目标选择流程，再把流程拆成可组合的任务。

总体思路如下：

```text
确定文书目标
（入院记录 / 病程记录 / 出院记录 / 病案首页等）
        ↓
明确该类文书需要的信息
        ↓
从相应来源获取信息
（既往病历 / 病情变化 / 检验 / 检查 / 医嘱等）
        ↓
识别与提取
        ↓
文本清洗、字段整理与结构化
        ↓
按模板组织内容
        ↓
工作流执行与结果核对
        ↓
由医务人员确认后使用
```

项目尝试的主要处理链路为：

**信息采集 → 信息识别 → 文本处理 → 文本整合 → 文书填写辅助**

其中，“文书填写辅助”是自动化操作探索，并不意味着目前所有文书均已实现完整、稳定的自动写回。

## 3. 我的设计思路：先分清信息，再决定用什么技术

### 3.1 先明确“要写什么”，而不是先写自动化脚本

入院记录、病程记录、出院记录和病案首页的目标不同，依赖的信息也不同。例如，病程记录可能需要病情变化、检验检查结果和医嘱状态；部分病情变化并不存在于系统中，需要医生用简短描述补充。因此，第一步应当是明确文书目的、必要信息与信息来源，再进入相应的工作流。

### 3.2 对结构较稳定的信息，优先使用规则与模板

对于系统中已有、格式相对稳定的信息，可以尝试通过明确的提取规则、字段映射和模板进行组织。此类任务的目标是忠实搬运、整理和格式化既有事实，通常没有必要让大语言模型重新生成内容。

这也是项目的一项重要原则：**能用明确规则完成的步骤，尽量不交给大语言模型自由生成。** 这样更容易追溯信息来源，也能降低模型编造或改变临床事实的风险。

### 3.3 对“真实世界脏数据”，再探索 OCR 与大语言模型

这里的“脏数据”是本项目语境下的工作称呼，指来源和格式不统一、难以直接结构化的资料，例如院外病历、纸质检验单、检查报告或保存在手机中的图片。

这类数据可能受到光照、拍摄设备、分辨率、版式和文字布局影响。传统 OCR 或固定规则未必能稳定提取目标信息，因此我进一步尝试了图像预处理、OCR、正则化，以及大语言模型辅助的信息提取。

在个人探索性测试中，我使用过不同量化设置的 Qwen 模型，对数十张不同光照、设备和分辨率下拍摄的血常规报告图片进行识别与信息提取尝试，并与非大语言模型 OCR 方案进行比较。我的观察是，在这批有限样本和特定提取任务中，大语言模型方案的结果具有较好的可用性，配合规则化处理后更容易转换为所需格式。

**这属于个人探索性测试，不是严格的标准化基准评测；相关实验也不代表已经完整集成到主程序，更不意味着模型输出可以未经核对直接用于临床。** 公开仓库不提供真实报告图片或患者数据。

### 3.4 用“原子工作流 + 编排”组织自动化

复杂任务由许多较小的操作组成，例如定位界面、点击控件、输入文本、等待页面响应、识别区域以及执行后续步骤。项目尝试将这些操作拆成原子工作流，再通过编排关系组合成更长的任务流程。

这样做的好处是：某个步骤出现问题时，可以相对独立地调试；同类操作也更容易复用；流程调整时，不必每次重新编写一整条脚本。

### 3.5 把医生保留在关键确认环节

本项目的目标是减少重复操作，不是自行补全未知的病情、诊断或治疗事实。必要信息缺失时，应由医生补充；对识别、整理或填写的内容，也应在使用前进行人工核对。自动化流程不能替代临床责任和医疗质量控制。

## 4. 当前架构（文字版）

```text
程序入口：月亮副驾V1.06/main.py
        ↓
用户界面层
├─ 主窗口
├─ 任务配置窗口
├─ 编排配置窗口
├─ 执行面板
├─ OCR面板
├─ 硬件控制/采集卡面板
└─ 登录对话框（开发测试用，默认关闭）
        ↓
任务与工作流层
├─ 任务管理器
├─ 工作流引擎：执行单个原子工作流
└─ 编排引擎：组合多个工作流并处理成功/失败分支
        ↓
核心处理层
├─ 页面定位函数
├─ OCR结果与缓存
├─ 文本处理调度器
├─ 文本处理器注册表
└─ 硬件管理器
        ↓
识别与文本处理层
├─ OCR引擎：不同像素尺寸/显示条件下的识别尝试
└─ 文本处理器：检验、检查、医嘱、病历内容等结果整理
        ↓
输入与设备层
├─ 采集卡与帧缓存
├─ CH9329键盘/鼠标控制
└─ 手机文件传输工具
        ↓
配置层
├─ JSON工作流
├─ JSON编排
└─ 任务配置

独立实验：大语言模型辅助的报告图片信息提取（尚不等同于主流程已集成）
```

## 5. 技术模块

| 模块 | 使用或探索的技术 | 在项目中的用途 |
|---|---|---|
| 桌面界面 | Python、PyQt5；部分独立工具使用 Tkinter | 主窗口、执行面板、任务配置、OCR调试、硬件操作界面 |
| 工作流 | JSON 配置、原子步骤、流程编排、条件分支 | 将重复操作拆分、配置并组合执行 |
| 图像处理 | OpenCV、NumPy | 图像读取、区域裁剪、颜色过滤、二值化、模板匹配等 |
| 特定场景 OCR | 字符模板/位图匹配、哈希检索、滑动窗口、固定区域（ROI）与行检测 | 探索在字体、颜色和显示位置相对稳定时进行识别 |
| 文本后处理 | Python 字符串处理、正则规则、处理器注册与调度 | 清洗识别结果、表格切分、字段整理与结构化输出 |
| 桌面输入控制 | CH9329、串口通信、模拟键盘/鼠标 | 在测试环境中执行预设键鼠操作 |
| 图像采集 | 采集卡、帧缓存 | 获取目标画面并向识别模块提供图像 |
| 文件传输 | 局域网网页上传与文字提交工具 | 辅助将文件或文字传入本地处理流程 |
| 大语言模型实验 | Qwen 量化模型、规则/正则化后处理 | 探索对非标准报告图片进行目标字段提取；属于独立探索，未验证为完整生产流程 |
| 开发方式 | AI-assisted coding | 借助 AI 工具进行代码生成、解释、调试和迭代；本人负责场景理解、需求拆解、流程/模块设计、集成测试与优化 |

> 说明：以上列出的是项目中已经使用或探索过的技术，不代表每个模块都已达到生产级质量，也不代表所有技术均已集成到同一条完整自动化链路中。

## 6. 当前完成情况

### 已形成代码框架或模块

- PyQt5 桌面端主界面及功能面板；
- 任务配置与 JSON 工作流编辑工具；
- 原子工作流执行与多工作流编排框架；
- OCR 引擎接口及多种特定场景识别实现；
- OCR 结果结构、文本处理器注册与调度机制；
- 图像定位、颜色处理和图像预处理工具；
- 采集卡、帧缓存、CH9329 键鼠控制等硬件相关模块；
- 手机文件传输的辅助模块。

### 已做的前期验证

在病案首页相关流程的早期受控测试中，原型能够替代约 **80% 以上的人工填写步骤**，减少近百次键盘/鼠标交互，单次流程耗时可控制在 **2 分钟以内**。

这些数字来自单一场景的前期原型测试，是个人测试记录，不是独立审计或标准化性能评估。它们不能外推到其他文书或不同医院系统。

### 尚未完成或未充分验证

- 入院记录、病程记录、出院记录等多类文书的完整闭环；
- HIS/CIS 等多个来源之间的信息获取、校验与流程整合；
- 院外报告图片的大语言模型提取与主程序之间的完整集成；
- OCR 对不同页面、字体、分辨率和布局的泛化能力；
- 全流程异常恢复、系统化测试与可复现评估；
- 面向其他电脑和硬件环境的一键安装与完整运行验证；
- 生产部署、正式医疗系统接入和合规审核。

## 7. 运行环境与硬件

建议运行环境：

- Windows 10 或 Windows 11；
- Python 3.11；
- PyQt5 及项目所需的图像处理、串口等 Python 依赖。

若要测试采集卡与硬件键鼠控制链路，还需要：

- CH9329 键鼠模拟硬件；
- 支持 RGB24、1080p、60 Hz 的视频采集卡；
- 与电脑及目标设备相匹配的连接线和接口。

部分 OCR、配置或界面模块可以单独研究；采集卡及 CH9329 相关流程需要对应硬件。当前项目仍在整理公开版运行步骤，尚不能承诺所有模块在全新电脑上开箱即用。

## 8. 隐私与安全

公开版本不应包含真实患者信息、真实病历/报告、医院账号密码、访问令牌、内部网络信息或未经授权的系统文件。展示截图与 Demo 应使用虚构数据和模拟界面；字体位图、哈希缓存等二进制资源不随公开版本提供。

本项目未经过生产级安全测试，不应连接生产医疗系统或在真实患者数据上运行。实际使用前还需完成授权、隐私保护、数据安全和医疗合规方面的评估。

## 9. 项目定位与后续方向

这是一个由临床场景出发的个人原型项目，重点是探索：

**临床流程理解 → 问题拆解 → 原子化工作流 → 信息识别与规则处理 → 自动化原型验证。**
